O microbenchmark de sync executou sequencialmente conjuntos virtuais de 1/5/10 usuários, cinco rodadas por implementação, 500 fatos e 500 status por usuário; não é benchmark de chamadas de API concorrentes.

## Diagnóstico e alteração justificada

`Motoboy/app.js:getSyncStatus()` fazia três leituras IndexedDB sequenciais depois das leituras paralelas iniciais e, para cada fato pendente, percorria linearmente a lista de status (`Array.find`). Isso repetia buscas até O(fatos × status). A correção lê `deliveryEvents`, `locations` e `proofs` em paralelo com os dados existentes e cria um `Map` de status `operation:` uma única vez, preservando a primeira entrada duplicada para manter a semântica anterior de `find`. O helper está em `sync-reconciliation.js`; teste unitário cobre filtragem e resolução.

Comparação do microbenchmark (mil fatos/statuses por usuário somados; p50 de cinco rodadas; medido no mesmo processo/dispositivo):

| Clientes virtuais | Implementação antiga p50 / p95 / p99 | Map p50 / p95 / p99 | Ganho de p50 |
|---:|---:|---:|---:|
| 1 | 9,269 / 18,545 / 18,545 ms | 2,005 / 2,293 / 2,293 ms | 4,62× |
| 5 | 33,426 / 33,778 / 33,778 ms | 7,830 / 8,781 / 8,781 ms | 4,27× |
| 10 | 36,058 / 45,576 / 45,576 ms | 15,448 / 17,238 / 17,238 ms | 2,33× |

Os percentis altos são instáveis com cinco amostras e CPU móvel concorrida; o dado sustenta redução para o conjunto testado, não previsão de latência de produção. O script reprodutível é `tests/benchmark-sync-status.js`, chamado por `npm run bench:sync-status` no Motoboy.
