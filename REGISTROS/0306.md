## Solicitação e correção da auditoria anterior

O proprietário esclareceu que há Nginx, backend oficial e backend E2E configurados e perguntou por quais rotas os serviços passam e por que as duas APIs estavam indisponíveis. A classificação anterior de 404 como efeito de “servidor estático” foi incompleta: os servidores estáticos foram iniciados pelo teste de browser nas portas de upstream 8788/8789 e mascararam o encaminhamento normal; além disso, não investiguei os virtual hosts antes da conclusão. Esta atualização substitui aquela interpretação para os 404 observados no browser, sem apagar o registro 0305.

## Rotas observadas

- Oficial: Restaurante `127.0.0.1:8081` e Motoboy `127.0.0.1:8082` encaminham `/api/*` para a API oficial em `127.0.0.1:8788`.
- E2E: Restaurante `127.0.0.1:8083` e Motoboy `127.0.0.1:8084` devem encaminhar `/api/*` para a API E2E em `127.0.0.1:8787`.
- Os scripts dos serviços confirmam oficial `PORT=8788` (`scripts/official-api-runtime.js`) e E2E `PORT=8787` (`server.js`, `NODE_ENV=test`). O template versionado `ops/nginx/rotamoto-restaurante-e2e.conf` já apontava para 8787.

A configuração instalada `/data/data/com.termux/files/usr/etc/nginx/rotamoto-restaurante-e2e.conf` estava divergente: suas quatro diretivas de upstream apontavam para 8788, compartilhado com o oficial. Isso poderia mandar chamadas do Restaurante E2E para o backend oficial se ambos estivessem ativos.

## Ação aplicada

Foram alteradas somente as quatro referências `127.0.0.1:8788` para `127.0.0.1:8787` no virtual host instalado do Restaurante E2E, alinhando-o ao serviço E2E e ao template do repositório. A configuração anterior foi preservada em `/data/data/com.termux/files/usr/tmp/rotamoto-restaurante-e2e.conf.codex-backup-20261109`. `nginx -t` passou e o Nginx recebeu reload controlado. Nenhum arquivo de código dos apps, template versionado, configuração do PostgreSQL ou dado foi alterado.

## Causa dos processos API indisponíveis

- Oficial: `rotamoto-api-official/run` exige `~/rotamoto-data/official-api/runtime.env`, arquivo regular próprio e modo 400/600. A raiz privada e o arquivo estão ausentes; pelo guard do `run`, o serviço encerra com status 111 antes de executar `scripts/official-api-runtime.js`.
- E2E: o serviço está configurado com `E2E_RUNTIME_DATABASE_URL` para `rotamoto_e2e`/`rotamoto_e2e_app` e keystore fora do repositório. Os caminhos configurados para diretório do keystore e chave mestre resolvem sob `~/rotamoto-data`, cuja raiz não existe. A validação não destrutiva com `createFileSecretProvider` falhou com `ENOENT` ao verificar essa raiz; o server carrega esse provider no bootstrap.
- PostgreSQL estava aceitando conexões. `psql` autenticou e leu somente `current_database()`/`current_user` como `rotamoto_app` em `rotamoto` e `rotamoto_e2e_app` em `rotamoto_e2e`. `.pgpass` está presente com modo 600.
- Runit reportou ambos os serviços API `down`; Nginx permanece `run`. Health checks por 8081–8084 retornaram 502 porque os backends em 8788/8787 não estavam escutando.

Não foi criada chave nova, refeito runtime.env, restaurado backup privado ou iniciado qualquer API. Recriar o keystore E2E sem recuperar sua chave mestra e envelopes existentes poderia invalidar referências configuradas (incluindo assinatura QR); configuração oficial pode conter referências privadas de SMTP/operador. A restauração precisa usar os arquivos originais/backup confiável. Não houve leitura de credenciais.

## Verificações

- `nginx -t -p /data/data/com.termux/files/home/.nginx -c /data/data/com.termux/files/usr/etc/nginx/nginx.conf`: PASS.
- `nginx -s reload` com o mesmo prefixo e arquivo de configuração: executado após `nginx -t`.
- Inspeção de `proxy_pass`: oficial 8081/8082 → 8788; E2E 8083/8084 → 8787 após correção.
- `sv status`: Nginx RUN; APIs oficial e E2E DOWN.
- Health checks GET: 8081, 8082, 8083 e 8084 retornam 502 até recuperação dos runtimes.
- PostgreSQL: login somente leitura das duas roles runtime PASS.
- Provider E2E: falha de validação read-only em `ENOENT` na raiz privada ausente.

## Estado e próximos passos

A rota E2E não aponta mais ao backend oficial. Os dois serviços continuam indisponíveis, sem acesso browser autenticado ou bootstrap operacional. Próximo passo é localizar/restaurar com segurança o `runtime.env` oficial e a árvore original do keystore E2E a partir de backup confiável; depois validar modo/owner, iniciar os serviços sob runit e confirmar health/readiness em 8081–8084. Não gerar secrets nem mudar banco/migrations como workaround.

Apps: sem modificações, commits ou push. Termux: uma configuração Nginx corrigida com backup preservado; teste de sintaxe e reload aprovados. Histórico: relatório e evidências desta investigação serão registrados em commit próprio deste repositório, sem alteração dos repositórios de aplicação.
