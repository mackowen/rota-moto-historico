# REGISTRO 0274 — HTTP 502 e validação operacional de autoNext

**Resultado: PASS_SCOPE** para o runner E2E, endpoint de instalação e cenários operacionais sintéticos A–D. Não representa homologação física Android nem aprovação global do produto.

## Causa comprovada do HTTP 502

A evidência Browser da 0272 registra `502` em `/api/sync/pull`; o texto da campanha atribuiu o erro a `/api/sync/installations/motoboy`. O log do nginx E2E mostrou `connect() failed (111: Connection refused)` para o upstream `127.0.0.1:8787`: o proxy não alcançava a API E2E. O handler real de `POST /api/sync/installations/motoboy` existe em `backend/domain/sync-http.js`, autentica a sessão/CSRF e registra a instalação idempotentemente por empresa/aplicativo.

A causa operacional foi a ordem de teardown no runner: `runFixtureLifecycle` podia fechar a API e reverter a fixture quando a callback terminava ou falhava, enquanto o Chromium ainda mantinha uma página ativa e podia disparar retry/sync. Assim, a falha era upstream indisponível durante teardown, não resposta 502 do handler. O runner também iniciava uma sincronização adicional antes de `syncBootstrapReady` concluir em algumas execuções. Não foi encontrada falha no código de produção nem incompatibilidade contratual.

A menor correção ficou no Browser Tests: o Chromium é encerrado no `finally` da callback, antes de o lifecycle desfazer a fixture/fechar a API; sincronizações explícitas aguardam o bootstrap autenticado e a leitura canônica. Não foram adicionados mocks, retries infinitos ou respostas substitutas. O endpoint retornou HTTP 200 tanto na verificação direta autenticada quanto no Browser. O log anterior de nginx foi consultado somente para diagnóstico e não foi copiado ao histórico.
