O runner autenticou Restaurante e dois perfis Chromium independentes de Motoboy, usando identidades sintéticas. A interface do Restaurante criou três Orders e três Deliveries e salvou uma Route com a sequência canônica das três entregas. A atribuição permaneceu sob autoridade do Restaurante.

O Motoboy aceitou e coletou a primeira entrega. Após o cancelamento autorizado pela interface do Restaurante, o runtime criou exatamente uma Delivery do tipo RETURN. O RETURN foi anexado depois das duas entregas pendentes, sem alterar a ordem relativa delas. As outras duas foram concluídas pela interface do Motoboy e o PostgreSQL E2E confirmou ambas como `DELIVERED` antes de executar o retorno.

O Motoboy registrou início, chegada e entrega física do RETURN. A interface do Restaurante confirmou o recebimento. O PostgreSQL E2E terminou com a entrega original `CANCELLED`, as duas entregas pendentes `DELIVERED`, o RETURN `RETURNED` e a custódia `RECEIVED`.

## Diagnóstico e correções

Não foi confirmado defeito de produto. O primeiro bloqueio foi uma expectativa inválida do runner: o cancelamento interno após coleta cria RETURN atomicamente; não existe uma segunda decisão RETURN nessa interface. Outros bloqueios eram de automação: confusão entre IDs locais e canônicos ao montar Route, seleção de linha em aba oculta e modal de pedido aberto cobrindo a navegação. O runner agora mapeia IDs via IndexedDB, exige visibilidade real, clica o título da entrega e fecha o modal pelo controle existente. Uma asserção espera o estado canônico `DELIVERED`, e não somente a tela local de conclusão.
