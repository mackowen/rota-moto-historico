# Campanha 0239 — Reset controlado do E2E e prova de Bootstrap

**Data:** 2026-10-17
**Resultado:** BLOCKED antes de qualquer limpeza ou Bootstrap persistente.
**Escopo:** somente auditoria read-only de `rotamoto_e2e`, validação dos serviços e tentativa de backup E2E. `rotamoto` não foi conectado nem alterado.

Baselines mantidas. Nenhum commit/push foi feito nos aplicativos.

## Auditoria e isolamento

- PostgreSQL, Nginx, API E2E e API oficial estavam `run` no runit. As interfaces web em 8081 e 8082 responderam HTTP 200. As raízes das APIs em 8787/8788 responderam 404, comportamento esperado para rotas não montadas; não foi tratado como health check.
- O `run` E2E fixa `NODE_ENV=test`, `127.0.0.1:8787` e `E2E_RUNTIME_DATABASE_URL=.../rotamoto_e2e`. O `run` oficial valida privadamente `NODE_ENV=development`, `127.0.0.1:8788` e `DATABASE_URL=.../rotamoto`, sem `MIGRATOR_DATABASE_URL`. Nenhuma configuração privada ou segredo foi lido.
- Conexões autenticadas como `rotamoto_app` e `rotamoto_migrator` confirmaram `current_database=rotamoto_e2e`, host loopback e seus papéis corretos. O serviço E2E estava ativo; a amostra de `pg_stat_activity` não mostrou sessão de API E2E naquele instante. Não foi iniciado nem parado serviço.
- Limite encontrado: `rotamoto_app` tem privilégio `CONNECT` nos dois bancos (sem `CREATE` em nenhum). Os processos têm URLs fixas e distintas, mas o papel runtime do E2E não está isolado por ACL de banco; a contenção de processo/configuração não satisfaz isolamento absoluto. Não foi testada conexão a `rotamoto` nem alterado seu ACL.
- Os papéis app, migrator, auditor, backup e restore existem. `rotamoto_app` e `rotamoto_migrator` não têm `BYPASSRLS`; `rotamoto_backup` tem `BYPASSRLS`, mas não possui `CONNECT` em `rotamoto_e2e`. Não houve alteração de grants. A autenticação do auditor não foi necessária para as consultas realizadas.
- `NODE_ENV=test ... migrate.js status --e2e` completou e confirmou as 47 migrations até `0047_administrative_mfa_recovery`; o runner rejeita checksums divergentes. O schema `rotamoto` tem 51 tabelas e 128 índices; 39 tabelas têm RLS habilitado e FORCE. Integridade estrutural detalhada não foi declarada integral porque reset/restore não ocorreu.
- Foram encontrados 17 schemas de campanhas de teste, totalizando 777 tabelas; 641 estão sob RLS FORCE. São resíduos sintéticos de fixtures antigos e precisam ser cobertos por um backup autorizado e inventário de teardown antes de qualquer limpeza. Nenhuma tabela, mídia ou schema foi apagado.
- A linha singleton `installation_bootstrap` está inicializada. A migration 0045 impede rollback quando há histórico de bootstrap e a migration 0046 recusa sempre remover sua proteção. O teste existente zera o latch somente dentro de uma transação fixture que termina em `ROLLBACK`; não existe contrato encontrado para reset persistente.

## Gate de backup: falha impeditiva

Foi tentado `pg_dump` custom-format apenas de `rotamoto_e2e`, autenticando como `rotamoto_migrator`, com staging privado em modo 0700 e arquivo 0600. O dump falhou em tabela com `FORCE ROW LEVEL SECURITY`: o migrator não pode ler todas as linhas. A role `rotamoto_backup` tem `BYPASSRLS`, mas a conexão a `rotamoto_e2e` é negada por ausência de `CONNECT`. Não foram concedidas permissões adicionais nem usado um bypass de RLS.

O staging parcial (5.469.286 bytes) foi removido logicamente após a falha; armazenamento flash não garante apagamento físico. Nenhum backup completo foi produzido e nenhuma restauração foi tentada. Assim, G2 não passa. Sem backup restaurável, a limpeza autorizada não pode começar. A falta de procedimento suportado para reinicializar o latch também bloquearia o Bootstrap mesmo após o backup.

## Fases não executadas

Não houve DELETE/TRUNCATE/DDL, alteração de latch, migration, criação de proprietário, convite, envio de email, MFA ou escrita de dados no E2E. O banco oficial `rotamoto` não foi consultado nem alterado. Não foram executadas jornadas Browser, fluxos autenticados, suites contra o E2E compartilhado ou reinícios de serviços, pois dependem de uma instalação limpa/restaurável e poderiam gerar dados concorrentes.

Para retomar com segurança, o operador precisa disponibilizar um caminho aprovado de backup E2E que leia todas as linhas sob FORCE RLS e possa ser restaurado em destino descartável, sem modificar grants do schema operacional. Em seguida, o contrato precisa fornecer um reset explícito, auditável e limitado ao E2E para os resíduos sintéticos e para o latch, ou provisionar um banco descartável isolado para a prova completa. Não usar `ALTER TABLE ... NO FORCE`, limpeza manual do latch nem SQL improvisado.
