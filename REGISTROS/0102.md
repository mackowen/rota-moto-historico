## Arquitetura, segurança e PII

Fluxo necessário: `provider webhook/poll → autenticação/assinatura raw bytes → resolver conta confiável → tenant → durable inbox/idempotência → normalização → Order canônico → domínio → durable outbox → worker → provider → reconciliação`.

- `integrations`/`external_accounts`, `provider_event_inbox`, `provider_command_outbox`, `provider_quotes`, `provider_tracking_snapshots`, `secret_ref` e worker existente podem ser reutilizados como base. Inbox/outbox e worker atuais são centrados em `logistics_providers` e Delivery/Fulfillment. Não há ingest de marketplace Order, webhook/account resolver ou Order inbox; a inbox não tem chave explícita de `integration/external_account`.
- Worker logístico reivindica comando via lease e a chamada HTTP ocorre fora da transação longa. Extensão marketplace precisa preservar isso.
- Account routing ainda não prova cross-tenant end-to-end: resolver deve usar vínculo confirmado, nunca merchant/shop ID isolado do payload. Keeta polling exige ID do Software Service por loja.
- Repository administrativo filtra por `company_id`; schema existente tem RLS/FORCE e FKs tenant-scoped. Sem account resolver, adapter isolado não prova tenant isolation.
- OAuth state/callback/revogação não wired. Keeta state é carregado no redirect URI; falta persistência/uso único/verificação no callback. iFood userCode flow não está montado.
- iFood/Keeta raw-body verifier aplica HMAC antes de parsear, tamanho máximo e timing-safe compare. Keeta orderURL não é seguido; redirects externos são rejeitados e response tem limite. URL auth Keeta só HTTPS/host documentado.
- Tokens/segredos não chegam ao frontend/logs. `secret_ref` não é acessível pelo runtime app role. Keeta app token não é persistido; iFood tokens cacheados em memória.
- Eventos normalizados não persistem payload bruto/PII. iFood mantém apenas dados operacionais mínimos de cliente/endereço; Keeta descarta PII protegida, mas precisa boundary oficial `batchDecrypt` para fulfillment.
- Chaves de idempotência/leases cobrem provider logistics atual, não Orders marketplace. Duplicata/replay/out-of-order marketplace ainda não testados end-to-end.
- Erros 401/403, 429/Retry-After, 5xx e timeout são classificados; GET 404 iFood tem retry bounded. Side effect 202 retorna pending; timeout de side effect é resultado ambíguo sem retry cego. Retry persistente e reconciliação de Order ainda não wired.
- `Order.source` continua canal comercial, separado de logistics provider/fulfillment. Courier externo não vira Driver e tracking externo não vira LocationPoint.
