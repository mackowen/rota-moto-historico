- Consulta catalogal via sessões já autorizadas comprovou `u0_a436` como role LOGIN/SUPERUSER e owner do database oficial `rotamoto`; `postgres` não existe neste cluster. O schema `rotamoto` e ledger/objetos são owned por `rotamoto_migrator`; database/schema E2E são owned por migrator.

Contém entradas para app, migrator, backup e restore; não contém entrada para `u0_a436`. `psql -U postgres` não foi usado como prova de ausência administrativa. Login `-w` como `u0_a436` também não autenticou (`fe_sendauth: no password supplied`). Não foi usado trust, reset de senha, single-user mode, elevação do migrator nem criação de superuser.

- Filesystem local foi escolhido, sem cloud/hostname/credencial inventada. A canonical query, via `rotamoto_backup`, retornou zero DeliveryProof/blob `filesystem-v1` ativos no oficial. Por isso foi criado um root local privado vazio para mídia desta campanha; ele não foi apresentado como storage operacional com conteúdo prévio.
- Chave de backup gerada pelo comando oficial `backup-key-init` com CSPRNG: 32 bytes, owner do serviço, modo 0600, link count 1. Diretórios de recovery/media e auditoria: privados modo 0700; audit file 0600. Recovery sets e chave de campanhas anteriores foram preservados.
- Keystore local foi inicializado pelo `initialize-local-keystore.js` com master key CSPRNG 32 bytes, modo 0600, diretório 0700. Nenhuma credencial foi armazenada nele. Antes de usar para senhas de serviço, a master key precisa de cópia operacional/offline protegida. O status development permanece `secrets=not_configured`; isso não impede backup/migration.
- `PUBLIC_BASE_URL` não é lido pelo `backup:create`, `backup:verify` ou migration runner. O backup e a migration abaixo passaram sem ele; URL HTTPS pública permanece pré-requisito apenas de callbacks OAuth/webhook e outros fluxos de deployment.
