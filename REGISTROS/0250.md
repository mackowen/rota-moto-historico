## Auditoria e causas confirmadas

1. **Exposição antes de resolver identidade.** O HTML montava a raiz operacional sem `inert`; o `identity-ui.js` só aplicava o bloqueio depois de iniciar. O backend seguia protegido, mas a interface tinha uma janela de renderização não fechada. O gate estático agora começa fechado nos dois HTMLs e a UI de identidade o libera segundo o estado da sessão.
2. **Permissões com identificadores internos.** O editor de perfis mostrava chaves como `company.manage`. A API já fornece descrições; a UI agora agrupa por finalidade e exibe a descrição, conservando a chave interna no valor enviado ao backend.
3. **Estado iFood descrito incorretamente.** Uma resposta HTTP válida do endpoint de estado interno gerava a mensagem “Conexão com o serviço iFood verificada”, mesmo sem teste de rede com a plataforma. A mensagem agora esclarece que apenas atualiza o estado registrado no RotaMoto e não confirma conectividade externa.
4. **Administração e acesso do motoboy.** O código existente mantém páginas separadas Empresa/Equipe/Motoboys/Integrações, e o backend Motoboy já exige membership/Driver ativo e permissões. Esta campanha reforçou o gate de primeiro render. As páginas administrativas autenticadas não foram carregadas no browser; não se afirma prova visual de todos os formulários.
